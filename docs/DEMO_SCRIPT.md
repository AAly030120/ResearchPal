# ResearchPal · 现场演示剧本（DEMO_SCRIPT.md）

> 目标：**5 分钟内让面试官看到「真东西」**，而不是看你注册账号、等建索引。
> 核心原则：**现场只演示「检索与生成」，不演示「建索引与建图」**（后者全部提前跑好）。

---

## 一、演示前 24 小时必做（Checklist）

| # | 事项 | 为什么 |
|---|------|--------|
| 1 | 确认 `Keep Demo Alive` workflow 在跑 | 否则冷启动 43 秒，面试官以为挂了 |
| 2 | 手动 ping 一次后端确认 200 | `curl -o /dev/null -w "%{http_code}" https://researchpal.onrender.com/openapi.json` |
| 3 | 在 Render 面板配好 LLM Key（或用演示账号自带 Key） | 否则所有回答走「未连接模型」文案 |
| 4 | 用 seed 脚本预置演示账号（见下） | 登录后直接看到已建好的图谱，不用现场等 |
| 5 | 录屏一份 3–5 分钟演示视频存本地 | **Plan B**：现场网络/后端出意外时直接播 |

## 二、预置演示账号

```bash
cd backend
python scripts/seed_demo.py
```

脚本会创建一个开箱即用的账号（默认 `demo@researchpal.dev` / `demo1234`），内含：

- 2–3 篇已上传的示例文献（PDF）
- **已完成的向量索引**（跳过现场等待）
- **已建好的知识图谱**（实体 / 关系 / 社区）

> 面试官登录后，Dashboard 应立刻显示「图谱已建 · N 实体」徽章。
> 这一步是演示成败的关键 —— 把耗时操作全部前置。

## 三、现场 5 分钟流程（照着念）

### 0:00–0:40 · 开场：抛痛点，不演示功能

> 「我做的不是又一个 ChatGPT 套壳。科研场景的真实痛点是：**文献读不完、引用对不上、跨论文的关联靠人肉记**。
> ResearchPal 的解法是三层：检索增强（RAG）解决『引得准』，知识图谱（GraphRAG）解决『连得上』，
> 深度研究 Agent 解决『写得出来』。」

*（注意：开场不要打开页面，先讲清为什么。面试官记住的是动机，不是按钮。）*

### 0:40–1:30 · 第一击：带页码的引用（证明「不胡编」）

- 打开**聊天页**，确认 RAG ✅ 与 图谱 ✅ 两个开关都亮着
- 提问：**「这几篇文献里，哪些方法在小样本上效果最好？」**
- 指着回答底部的来源面板说：

> 「每条结论后面都挂着来源，精确到**第几页第几段**，点开能看到原文片段。
> 这解决的是学术场景最致命的问题 —— 模型编造引用。」

### 1:30–2:40 · 第二击：知识图谱（差异化，别人没有）

- 切到 **Dashboard**，指出文件卡上的「图谱已建 · 87 实体」徽章
- 回到聊天页，问一个**跨文档**的问题：
  **「Transformer 和 GNN 在这几篇里分别被用在什么任务上？它们有没有共同作者或共同方法？」**

> 「纯向量检索答不了这种问题 —— 它只能找『相似的一段话』。
> 我把文献抽成实体关系图，做 N 跳扩展 + 社区摘要，所以能回答**跨文档的关联**。」

*（如果面试官是技术背景，补一句：Louvain 社区发现 + LLM 生成社区摘要，这是 GraphRAG 的做法。）*

### 2:40–4:00 · 第三击：深度研究 Agent（展示 Agent 设计能力）

- 打开**深度研究**开关，输入：**「帮我写一份关于图神经网络在药物发现中应用的综述」**
- 指着 streaming 的阶段提示（规划中 → 撰写第 N 节 → 整理参考文献）说：

> 「它不是一次生成，而是**先拆子问题，再逐节检索撰写，最后汇总引用**。
> 每个子问题独立检索，避免长上下文里信息被稀释。」

### 4:00–5:00 · 收尾：讲工程，不讲功能

> 「线上跑的是 Render 免费实例。它有个坑：**文件系统是临时的，一重启数据全没**。
> 我早期的处理是本地 SQLite，结果用户反馈『账号莫名其妙没了』。
> 后来改成 Postgres 存结构化数据，上传文件原始字节存 BYTEA，重启后自动还原到磁盘，
> 向量库再由后台自愈任务重建。**

*（这一段比任何功能都值钱 —— 它证明你真的上线过、真的被现实教育过。）*

## 四、高频追问预备

**Q：无 Key 时为什么是「自带密钥」模式？**
> A：这是产品选择，不是没配好。学术工具的用户往往有自己的实验室 Key，
> 让他们自带既降低我的成本，也避免密钥泄露责任。密钥只存服务端，不落前端。

**Q：你怎么证明 RAG 有效？**
> A：`python scripts/bench_rag.py` 会跑一份召回评测，对比「纯向量召回」vs「重排后召回」
> 的命中率与延迟。数字在这里 ——（报出你本地跑出来的数）。

**Q：图谱抽取错了怎么办？**
> A：抽取结果落库时带 `confidence` 与 `source_chunk_ids`，能溯源到具体片段；
> 重新索引会先删旧图再重建，所以是幂等的，修一次 prompt 就能全量刷新。

## 五、Plan B（现场翻车时的救场顺序）

1. **后端冷启动** → 直接说「免费实例刚休眠，我预热一下」，同时播录屏
2. **LLM 无响应** → 切到另一个模型（设置页），或播录屏
3. **网络完全不通** → 播录屏 + 打开 GitHub 讲代码与架构图

> 永远不要现场 debug。面试官要看的是产品与判断力，不是排错能力。
